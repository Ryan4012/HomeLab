# October 3, 2026

## Worked On
- Migrating the monitoring stack (Uptime Kuma, Grafana, Prometheus) from Docker containers on the Raspberry Pi into the k3s cluster, while preserving existing data and keeping TLS access working.

## What I Did
- Joined the Pi to the k3s cluster as a third node (after fixing a missing cgroup memory controller via cmdline.txt), confirmed working alongside k3s-server-01 and k3s-agent-01.
- Validated local-path-provisioner persistent storage actually survives pod delete/recreate before trusting it with real data.
- For each of Kuma, Grafana, and Prometheus: created a PVC, used a throwaway "primer" pod to force PV creation, stopped the old Docker container, copied its data directory into the new PV's path on the Pi's disk, fixed ownership where needed, then deployed the real pod pinned to the Pi node via nodeSelector so it stayed co-located with its data.
- All three are now running as k3s pods, reachable via *.home.arpa URLs with HTTPS intact.

## Issues / Findings
- local-path-provisioner ties storage to whichever node the pod lands on — fine for a hobby cluster, but means node loss = potential data loss unless backed up separately.
- PVCs don't create their backing directory until a pod actually consumes them (WaitForFirstConsumer), which is why the primer-pod step was necessary before copying data in.
- Ownership mismatches matter: Prometheus and Grafana run as non-root UIDs in their official images, so copied data needed a chown to the right UID or the containers would fail to read their own files.
- Deployment strategy needed to be Recreate rather than the default RollingUpdate, since ReadWriteOnce PVCs can't be mounted by two pods at once during a rollover.
