## What I Did
- Wrote a Gitea Actions workflow for ansible-homelab that clones the repo fresh and runs ansible-playbook k3s-install.yml on every push, reusing the same clone-token pattern from the Terraform workflow.
- Confirmed the playbook is safe to re-run against an already-configured cluster — it just skips reinstalling k3s if it's already present, so triggering it via CI doesn't risk breaking the live nodes.
- Created a k3s-manifests repo with a first test manifest, a plain nginx pod to prove out the deploy pipeline before putting anything real through it.
- Wrote a deploy.yml workflow that clones the repo and runs kubectl apply -f against the test manifest, using the kubeconfig already set up on the Gitea LXC.
- Pushed both workflows, watched them go green in the Actions tab, and confirmed with kubectl get pods that the nginx pod actually came up on the cluster.

## Issues / Findings
- This closed the full loop I'd been building toward: push to Gitea → Ansible re-converges the nodes' config, push to Gitea → k3s deploys new workloads — both fully automated now, no manual SSH steps required for either.
- Deliberately started with a throwaway nginx pod instead of a real service, to isolate "does the pipeline work" from "does the workload config work", cheap way to catch pipeline issues without risking anything real.
- Thought through what's actually safe to put through this pipeline next: existing services like Postgres are staying put on the Debian VM for now, since Kubernetes persistent storage is a real unknown I haven't tested yet, and a botched database migration isn't worth the risk. New, low-stakes services are the better next candidates for actually living in k3s.
